# AGENTS.md

This file provides guidance to AI coding agents (e.g. Claude Code) when working with code in this repository.

## Commands

All commands run from `frontend/`:

- `npm run dev` — start the Vite dev server
- `npm run build` — type-check (`tsc -b`) then production build via Vite
- `npm run lint` — run oxlint (config in `.oxlintrc.json`)
- `npm run preview` — preview the production build

There is no test runner configured in this project.

## Architecture

This is a client-facing portal for "EcoVolt 360" (a solar-energy company), built with React 19 + TypeScript + Vite + Chakra UI v3. All UI copy is in Brazilian Portuguese.

**Routing**: `src/App.tsx` defines routes with `react-router-dom` (`BrowserRouter` → `AuthProvider` → `Routes`). All paths live in `paths` (`src/routes/routes.ts`); never hardcode them. Public: `/` (`LandingPage`), `/login` (`LoginPage`) and `/cadastro` (`RegistrationPage`). Authenticated routes are nested as `RequireSession` → `RequireRole` → `PanelBase`:
- `CUSTOMER`: `/cliente` (`CustomerPanelHome`) and `/cliente/chamados` (`SupportTicket`).
- `SUPPORT`: `/suporte` (`SupportPanelHome`) and `/suporte/chamados` (`TicketsQueue`).

`RequireSession` validates the token with `GET /session` before rendering (shows "Carregando...", or an offline screen with "Tentar novamente"), and syncs the role returned by the backend. Without a session it redirects to `/login?sessao=expirada`. `RequireRole` sends anonymous users to `/login` and a mismatched role to that role's home via `homePath(role)`. `PanelBase` is the shared layout (`Sidebar` + `Header` + `Outlet`). `Sidebar` links change by role and include the "Sair" (logout) button.

**Auth/session**: `src/context/AuthContext.tsx` provides `useAuth()` → `{ session, setSession, logout }`. `Session` (`role`, `name`, `accessToken`) is persisted in `sessionStorage` (key `ecovolt.session`) via `saveSession`/`loadSession`/`clearSession` in `routes.ts`. Login does `POST /login`, stores the session and navigates to `homePath(role)`. `logout` does `POST /logout` and returns to `/login`, showing an error toast if it fails. When the login page opens with `?sessao=expirada` it shows a "Sessão inválida ou expirada" toast and strips the param.

**API layer**: `src/api/api.ts` is the shared axios instance (`baseURL` `http://localhost:8080`). A request interceptor adds `Authorization: Bearer <accessToken>` (except on `/login`), and a response interceptor handles any 401 (except `/login`) by clearing the session and redirecting to `/login?sessao=expirada`. Domain calls go in `src/api/<domain>.ts`: `src/api/tickets.ts` holds ticket types (`CustomerTicket`, `TicketCategory`, `TicketMessage`), `categoryLabels`/`categoryLabel`, mapping from API DTOs (uppercase status/category, date formatted as pt-BR), request functions (`listCustomerTickets`, `listSupportTickets`, `listTickets`, `evaluateTicket`, `updateTicketStatus`, `updateTicketCategory`, `getTicketMessages`, `sendTicketMessage`), and loading hooks (`useCustomerTickets`, `useSupportTickets`, `useAllTickets`) that return `{ tickets, error, loading }`. Shared status types and `ticketStatusLabels` live in `src/models/ticketStatus.ts`. To tell the user the server is unreachable, check `axios.isAxiosError(error) && !error.response`.

**Chakra setup**: `src/main.tsx` wraps the app in `ChakraProvider` using `defaultSystem` (no custom theme extension yet). Components mix Chakra primitives (`Box`, `Flex`, `Field`, `Input`, `Button`, `Avatar`, `Checkbox`, etc.) with hand-written BEM-style CSS classes and a colocated `.css` file per component/page (imported directly). `RegistrationPage` has moved to **CSS Modules** (`*.module.css`, imported as `styles`): its TSX uses Chakra components (`Box`, `Flex`, `Heading`, `Image`, `Field`, `Input`, `Button`, `Icon`, with `as` for semantic tags) styled via `className`, with no inline `style`. Sizing of Chakra components comes from Chakra itself (recipe props like `size`, plus sizing props such as `boxSize`, `width`, `minW`, `p`, `rounded`, e.g. the step dots and the "Cadastrar" button), while colors and typography stay in the CSS Module. Chakra recipes live in CSS cascade layers, so unlayered CSS Module rules override them. Styles are written mobile-first with `@media (min-width: 64rem)` as the main desktop breakpoint. Use this pattern when migrating other pages. `LandingPage` (`src/pages/LandingPage/`) follows it too: a hero with a background photo + gradient overlay (both applied via `url()` in the CSS Module), images in `src/assets/landing/`, top nav links that point to section ids (`inicio`, `faq`, `solucoes`, `sobre`, `contato`; only `inicio` exists yet) with a green accent line (`aria-current="location"`) under the section in view, updated on click and on scroll, and an "Entrar" button that goes to `paths.login` (or to `homePath(role)` if there is a session). Note: the global unlayered `img { height: auto }` in `index.css` overrides Chakra sizing props on `Image`, so size images in the CSS Module.

**Page structure convention**: each page lives under `src/pages/<PageName>/` with its own `.tsx` and `.css`. Multi-part pages further nest a `Components/` folder (e.g. `RegistrationPage/Components/RegistrationForms.tsx`) or split subviews into sibling files (e.g. `SupportTicket/SupportTicketList.tsx`), with page-specific modals in subfolders (e.g. `SupportTicket/SupportTicketModal/`, `SupportTicket/SupportTicketEvaluationModal/`). Shared components live in `src/components/`: chrome (`Header`, `Sidebar`), `TicketStatusBadge`, and `TicketDetailsModal/` (ticket details + paginated messages; for `SUPPORT` it shows `StatusDropdown`/`CategoryDropdown` to change status/category). `PanelBase` (`src/pages/PanelBase/PanelBase.tsx`) renders `Sidebar` + `Header` + the routed page.

**Forms**: `LoginPageForm` (Chakra `Field.Root`/`Input` markup) shows an error toast when email or password is empty, otherwise calls `POST /login` (see Auth/session), with distinct toasts for invalid credentials vs. no connection to the server. `SupportTicketModal` (new ticket) only validates title/description and shows a success toast, with no API call yet. `RegistrationForms` is a `chakra.form` (`noValidate`) with **controlled** Chakra `Field`/`Input`/`Button` styled via CSS Modules, and a two-step wizard (personal info → address). Both steps stay mounted (the inactive one uses `hidden`).
- Validation is hand-rolled (no form library) in `Components/registrationValidation.ts`: pure validators, `validateStep`, and every user-facing message in `validationMessages`, so change texts there. Fields are checked on blur and re-checked on change once they show an error. Advancing with "→" or the dots requires step 1 to be valid, and submit validates both steps, jumping back to step 1 if it has errors. Errors render through `Field.Root invalid` + `Field.ErrorText`, colored with the `--color-warning-*` tokens.
- Password rule: 8–25 characters with at least one letter and one number.
- CEP lookup is in `Components/viaCep.ts` (ViaCEP, `AbortController` cancels stale requests). Once 8 digits are typed it fills Estado/Cidade/Bairro/Rua with whatever is returned, and those fields stay editable. "CEP não encontrado" blocks submit, while a failed lookup doesn't, since the user can fill the address manually.
- `handleSubmit` builds the nested body and sends `POST /customers`. On success it shows a toast and navigates to the login (`/`). On 404 it marks the CPF with `validationMessages.cpfNotFound` and goes back to step 1. On 409 it shows the backend's `message`, and otherwise a generic error or connection error.

**Toasts**: `src/components/ui/toaster.tsx` exports both the Chakra `toaster` instance and the `<Toaster />` component, styled with the project's success/warning tokens (it renders title + description only, no close button). `<Toaster />` is rendered once in `src/main.tsx`, outside the router, so toasts survive route changes. Trigger them with `toaster.create({ type: "success" | "error", title, description })`; used across forms, modals, and `AuthContext`.

**Mock data pattern**: data that doesn't yet come from the API goes in colocated `*.mock.ts` files, which export the type and the mock consumed by the page. Today only the summary cards on the home pages use mocks (`CustomerPanelHome/customerPanelData.mock.ts` → `customerSummaryMock`, `SupportPanelHome/supportData.mock.ts` → `supportSummaryMock`). Ticket lists come from the API (`src/api/tickets.ts`). `SupportTicket/supportTicket.mock.ts` and `SupportPanelHome/supportTickets.mock.ts` aren't imported anywhere anymore (legacy), so don't use them as a source of types: use `src/api/tickets.ts` and `src/models/ticketStatus.ts`.

There is no state management library: global state is limited to `AuthContext`, and the rest is local component state.
